# RestoFlow 项目说明

## 1. 项目简介

RestoFlow 是一个仿美团餐饮收银系统的学习型 POS 项目，面向中小型餐饮门店的堂食场景。项目目标不是商业交付，而是通过一个真实业务，练习接近企业的软件开发方式。

## 2. 项目目标

| 目标类型 | 内容 |
|---|---|
| 学习目标 | 练习需求分析、设计文档、分层架构、状态机、事务等企业开发基本功 |
| 功能目标 | V1 跑通堂食核心闭环：桌台 → 开台 → 点餐 → 订单 → 厨房 → 结账 |

## 3. 项目范围

### 3.1 V1 范围

1. 桌台看板：按区域分组展示，状态（空闲/占用/待清台）实时刷新
2. 开台：选择空闲桌台，输入用餐人数
3. 点餐：购物车选菜，口味备注，沽清菜品拦截
4. 订单：开台即建单，支持加菜、退菜（未结账）、反结账
5. 厨房 KDS：明细状态流转 待制作 → 已出餐，退菜标记为已退
6. 结账：优惠/抹零、组合支付；结账后桌台进入待清台，清台为独立动作
7. 登录与权限：用户名密码登录，按角色控制业务模块的访问（模块级权限，管理员可维护用户与角色的关系）
8. 基础数据维护：菜品分类、菜品、桌台区域、桌台

### 3.2 暂缓清单（V1 不做，但设计必须可扩展）

| 暂缓功能 | 未来扩展方式 |
|---|---|
| 外卖 | 订单将来增加"堂食/外卖"类型字段即可扩展（V1 不预留字段），点餐流程可并行增加外卖入口 |
| 会员 | 结算时增加会员身份接入即可扩展，支付方式可扩展会员卡/储值（V1 不预留字段） |
| 优惠券 | 结账优惠从手动输入升级为规则匹配，订单结构不变 |
| 打印 | 出餐信息已由 KDS 展示，将来以浏览器打印方案接入，不改业务结构 |
| 交接班 | 所有交易已记录操作者，将来按操作者+时段聚合即可实现 |

> 营业报表、动态菜单、按钮级权限不在 V1 闭环内，归入后续阶段，由开发路线文档规划。

## 4. 用户角色

| 角色 | 职责 |
|---|---|
| 服务员 | 开台、点餐、加菜、退菜、结账 |
| 后厨 | 查看 KDS、操作出餐、设置沽清 |
| 店长 | 菜品维护、全部业务权限 |
| 管理员 | 用户与权限管理，可访问全部业务模块 |

## 7. 设计原则

1. **简单优先**：能用简单方案绝不用复杂方案，不为假设的需求提前写代码
2. **扩展预留**：每个核心设计点（订单、结算、桌台）都要考虑将来扩展外卖/会员/打印时是否会成为死路
3. **数据可靠**：金额精确、状态流转有校验、每个操作留痕
4. **文档驱动**：功能变更先改文档再改代码。落地方式：每次变更在 CHANGELOG.md 中记录，并在对应设计文档中同步更新，评审通过后方可进入编码

## 9. 术语表

| 术语 | 解释 |
|---|---|
| 开台 | 顾客入座后，服务员在系统中选择桌台并输入人数，开始一次用餐记录 |
| 清台 | 顾客结账离开后，服务员清理桌台并手动操作，使桌台恢复空闲状态 |
| 待清台 | 结账完成但桌台尚未清理的中间状态，此时桌台不可再次开台 |
| 沽清 | 菜品售罄标记，标记后点餐页不可再点此菜 |
| KDS | Kitchen Display System，厨房显示系统，后厨的出餐操作界面 |
| 反结账 | 撤销已完成的结账，订单回到未结状态，以便修改后重新结算 |
| 退菜 | 已下单未结账的菜品取消，明细标记为已退并记录原因 |
| 抹零 | 结账时舍去应收金额的零头 |
| 组合支付 | 一笔订单使用多种支付方式分别支付 |
| 购物车 | 点餐页暂存已选菜品的区域，下单后清空并提交厨房 |
