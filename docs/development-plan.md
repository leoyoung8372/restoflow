# RestoFlow 开发路线文档

## 1. 文档说明

- **目的**：把 6 份设计文档转化为可执行的开发顺序，是编码阶段的执行依据
- **使用方式**：按阶段顺序开发，每阶段完成后对照验收标准自查，通过后进入下一阶段；开发中发现设计文档的问题走变更流程（评审 → 改文档 → 记 CHANGELOG.md → 再改代码，project-overview.md 设计原则 4）
- **编号引用**：接口编号引自 api-design.md 第 4 章；需求编号引自 requirements-analysis.md；页面路由引自 system-design.md 5.1
- **切片说明**：阶段 0~2 为**基础能力与基础数据切片**（建立可运行的骨架与数据，不构成业务闭环）；阶段 3~5 为**业务垂直切片**（后端接口+前端页面同步完成，阶段结束即有可演示的业务成果）；阶段 6 为验收切片

## 2. 开发前置检查（阶段 0 的前置门槛）

进入编码前，须完成一次六文档一致性核对，发现不一致先走变更流程，核对通过后方可开始阶段 0：

1. **核心对象一致**：Order / OrderItem / Table / Dish / Payment / User 的表字段（database-design.md 第 4 章）↔ API 对象（api-design.md 第 3 章）↔ 状态码值（database-design.md 第 6 章为唯一权威码值表）
2. **状态机一致**：business-process.md 2.1~2.3 状态转换表 ↔ 数据库状态字段 ↔ api-design 接口校验，三方无出入
3. **范围无越界**：全部表与接口对照 V1 范围（project-overview.md 3.1）与暂缓清单（3.2），无越界设计

## 3. 阶段规划总览

| 阶段 | 主题 | 内容概要 | 依赖 |
|---|---|---|---|
| 0 | 项目初始化 | 前后端工程骨架、建表 SQL、技术基础设施 | 前置检查通过 |
| 1 | 认证与用户管理 | 1a 认证能力（登录、JWT、模块权限拦截）；1b 用户维护 | 0 |
| 2 | 基础数据 | 分类/菜品/区域/桌台维护 | 1a |
| 3 | 桌台与点餐 | 看板、开台、下单/加菜（内部顺序 3A→3D） | 2 |
| 4 | 厨房 KDS | KDS 展示、出餐、沽清 | 3 |
| 5 | 订单与结账 | 退菜、订单查询、结账全流程、反结账、清台 | 3、4 |
| 6 | 全链路验收 | 按五类场景逐条验证、缺陷修复 | 全部 |

阶段排序逻辑：认证能力先行（一切接口的前置）→ 基础数据先行（桌台/菜品是业务入口的依赖）→ 业务主线（开台→点餐→厨房→结账）→ 收尾。

## 4. 各阶段详情

### 阶段 0：项目初始化

**目标**：可运行的工程骨架与数据库就绪。

**开发内容**：

- 数据库：按 database-design.md 编写建表 SQL 并执行；种子数据仅一个初始管理员账号（admin，初始密码 123456，首次登录后由管理员自行修改）
- 后端骨架：Spring Boot 3 + Java 21 工程；统一返回结构、全局异常处理（api-design.md 2.7 错误处理约定）、knife4j 接入、数据库连接、MyBatis-Plus（包结构按 system-design.md 4.2）
- 前端骨架：Vue 3 + Vite 工程；axios 封装（统一拦截 401 跳登录、403 与错误提示）、路由、Pinia、主布局

**验收**：前后端工程可启动；knife4j 可访问；数据库表结构与 database-design.md 一致。

**学习点**：工程分层与包结构、统一约定落地。

**本阶段不做**：不实现任何业务接口与页面；不引入缓存、消息队列等架构外技术（system-design.md 第 8 章）。

### 阶段 1：认证与用户管理

**目标**：认证业务闭环（登录 → JWT 签发校验 → 模块权限拦截 → 401/403），用户维护可用。

**开发内容**：

- **1a 认证能力**：接口 #1 登录；Spring Security + JWT 签发与校验；模块权限拦截器（统一校验，api-design.md 2.4）；401/403 响应；页面：登录页 /login、首页 /
- **1b 用户维护**：接口 #32~35；页面：用户管理 /users

**验收**：AUTH-01①②③、AUTH-02、AUTH-03①②③、AUTH-04①②③、NF-05（BCrypt 存储）

**学习点**：Spring Security + JWT、拦截器统一权限校验、BCrypt、前端 401/403 拦截处理。

**本阶段不做**：不建角色/权限配置表与维护界面（权限矩阵为固定配置）；不做动态菜单与按钮级权限（暂缓清单）。

### 阶段 2：基础数据

**接口**：#2 桌台列表、#7 菜品列表（基础数据维护页复用）、#18~31（分类/菜品/区域/桌台维护）

**页面**：基础数据维护 /base

**验收**：BASE-01~04（含删除保护场景 4.7）

**学习点**：MyBatis-Plus 单表 CRUD、外键约束下的删除保护。

**本阶段不做**：菜品图片、排序、上下架等需求外字段；支付方式维护页面（BASE-05 预置）。本阶段完成≠业务闭环，它只为阶段 3 提供数据。

### 阶段 3：桌台与点餐

**接口**：#3 开台、#4 订单详情、#5 下单/加菜（#2 桌台列表、#7 菜品列表已于阶段 2 实现，此处复用）

**页面**：桌台看板 /table、点餐页 /table/order/:tableId

**内部开发顺序**（按事务边界拆，逐段验收）：

- **3A 看板与菜品数据**：复用 #2 桌台列表（看板按轮询方式调用）、#7 菜品列表，先打通看板与点餐页展示层
- **3B 开台**：#3 开台、#4 订单详情——开台即建单（ORDER-01），订单+桌台状态+日志为同一事务，**不可拆开实现**
- **3C 下单/加菜**：#5——购物车批量提交、快照落库、订单金额重算、日志
- **3D 联动验收**：轮询刷新（NF-04）、状态流转（空闲→占用）、currentOrderId 组装正确

**验收**：TABLE-01~03、POS-01~04、ORDER-01、ORDER-02、NF-04（看板 T1−T0 ≤ 5 秒，api-design.md 2.6）

**学习点**：三个状态机的落地与校验、开台/下单的多表事务、**前端轮询统一封装（usePolling，阶段 4 的 KDS 复用同一实现）**、currentOrderId 组装查询。

**本阶段不做**：清台（阶段 5，前置状态"待清台"只有结账后才出现）；结账/退菜/反结账（阶段 5）；KDS（阶段 4）；购物车持久化（购物车存前端 Pinia，刷新即弃）。

### 阶段 4：厨房 KDS

**接口**：#15 KDS 列表（轮询）、#16 出餐、#17 沽清/恢复

**页面**：厨房 KDS /kitchen

**验收**：KDS-01~03、POS-03（沽清联动点餐端）、NF-04（KDS T1−T0 ≤ 5 秒）

**学习点**：跨表组装查询（明细+桌台名）、明细状态流转、轮询封装复用。

**本阶段不做**：出餐回退（明细状态仅 待制作→已出餐 单向）；声音提醒、多屏分区等需求外能力。

### 阶段 5：订单与结账

**接口**：#6 清台、#8 订单列表、#9 退菜、#10 设置优惠与抹零、#11 收款、#12 取消结账、#13 完成结账、#14 反结账

**页面**：订单列表 /orders、结账页 /checkout/:orderId（反结账入口在桌台看板的待清台桌台）

**开发前必读**：

- **状态机联动**：核对 business-process.md 2.1（桌台）/ 2.2（订单）转换表——结账/反结账/取消涉及订单 × 桌台 × 支付记录三方联动，每个操作的目标状态组合以转换表为唯一依据
- **金额单一真相**：应收金额 = f(明细, 优惠, 抹零)，全部由后端重算（api-design.md 2.6、database-design.md 4.6 重算规则），**前端只提交原始输入（优惠金额、收款金额），不提交计算结果**——反结账→修改→再结账全程金额零漂移

**验收**：ORDER-03~05、PAY-01~04、TABLE-04（清台）、NF-03（开台/下单/退菜/结账/反结账/清台/收款留痕完整）

**学习点**：金额重算规则（退菜/优惠/抹零/反结账/取消）、支付记录失效机制（标记失效不删除 + 操作日志）、事务边界、角色例外校验（反结账仅店长）。

**本阶段不做**：结账后单品退款（V1 仅整单反结账）；发票与小票打印（暂缓清单）；营业报表（暂缓清单）；并发幂等机制（V1 由状态校验兜底重复提交：重复结账/重复出餐均被 409 拒绝）。

### 阶段 6：全链路验收

**内容**：按五类场景对照验收标准逐条验证：

1. **正常场景**：29 条功能需求的主路径
2. **异常场景**：business-process.md 4.1~4.8 逐项走查
3. **边界场景**：0 元订单结账、人数 1/99、优惠=原价、已收=应收临界、抹零角分、退菜致应收低于已收被拒
4. **权限场景**：四角色 × 5 模块权限矩阵逐一验证；反结账非店长 403；停用用户登录 403
5. **状态转换场景**：三个状态机转换表的每条合法转移 + 每条非法转移被 409 拒绝

缺陷修复后重复验证。

**完成标志**：全部验收标准通过，V1 堂食闭环可完整演示。验收阶段只修缺陷，不新增功能（新需求走变更流程）。

## 5. 里程碑与验收方式

- 每个阶段结束即一个里程碑：该阶段验收标准全部通过
- **验收方式：手工测试为主**，V1 不引入自动化测试框架（接口 35 个、场景有限，手工可覆盖；将来需要再评审引入）
- 测试数据：阶段 2 由店长角色录入运营数据（分类/菜品/区域/桌台），录入过程同时作为 BASE 功能验收的一部分

## 6. 变更约定

- 开发中发现设计文档的缺陷或歧义：先提出 → 评审确认 → 更新对应设计文档 → 记录 CHANGELOG.md → 再修改代码
- 阶段完成时在本文档总览表标注完成状态
