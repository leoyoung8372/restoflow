# RestoFlow 系统架构设计文档

## 1. 文档说明

- **目的**：定义技术选型、分层结构与关键技术决策，是代码结构设计与 api-design.md 的上游
- **设计原则**：技术决策优先满足 V1 业务闭环，不为未来扩展引入当前无需求的复杂方案
- **与需求的关系**：requirements-analysis.md 中的技术中立点（登录状态、数据刷新、权限校验等）在本文第 6 章落定，每条标注需求编号

## 2. 总体架构

```
┌──────────────┐  HTTP/JSON   ┌────────────────────────────┐   SQL   ┌──────────┐
│  Vue 3 SPA   │ ───────────▶ │       Spring Boot 3        │ ──────▶ │ MySQL 8  │
│  （浏览器）   │   REST API   │ Controller → Service →     │         └──────────┘
└──────────────┘              │ Mapper（MyBatis-Plus）     │
                              └────────────────────────────┘
```

- **前后端分离**：前端独立开发运行，通过 REST API 交互，数据格式 JSON
- **单体后端**：V1 规模不需要微服务，模块划分体现在包结构上

## 3. 技术选型

| 层 | 技术 | 用途 | 理由 |
|---|---|---|---|
| 后端语言 | Java 21 | 运行环境 | 长期支持版本 |
| 后端框架 | Spring Boot 3.x | 应用框架 | 生态成熟，企业主流 |
| 持久层 | MyBatis-Plus | ORM | 单表 CRUD 免手写，国内企业主流，与 MySQL 配合成熟 |
| 认证 | Spring Security + JWT | 登录认证 | AUTH-01/02 的实现，有效期 4 小时 |
| API文档 | knife4j | 接口文档生成与在线调试 | 开发期调试便利 |
| 数据库 | MySQL 8 | 数据存储 | 项目指定 |
| 前端框架 | Vue 3 + Vite | 页面开发 | 项目指定 |
| 组件库 | Element Plus | UI 组件 | Vue 3 生态成熟 |
| 状态管理 | Pinia | 前端状态 | Vue 3 官方推荐 |
| HTTP | axios | 接口调用 | 主流方案 |

## 4. 后端结构

### 4.1 分层

```
Controller（接口层：参数接收与校验、返回统一结构）
    ↓
Service（业务层：业务规则、状态校验、事务边界）
    ↓
Mapper（数据访问层：MyBatis-Plus）
```

### 4.2 包结构与模块划分

模块划分与权限矩阵的 5 个模块一一对应：

```
com.restoflow
├── common       # 统一返回结构、全局异常处理、状态枚举、常量
├── security     # 登录认证、JWT、模块权限校验（支撑层）
├── table        # 桌台模块：看板、开台、清台、点餐、下单（权限=桌台模块）
├── order        # 订单模块：订单查询、退菜、结账、反结账（权限=订单模块）
├── kitchen      # 厨房模块：KDS 展示、出餐、沽清（权限=厨房模块）
├── base         # 基础数据模块：分类、菜品、区域、桌台、支付方式（权限=基础数据模块）
└── system       # 用户管理模块：用户维护（权限=用户管理模块）
```

> 说明：加菜与首次点餐共用"下单"接口（业务上都是追加明细，见 business-process.md 3.2），归属 table 模块；退菜归属 order 模块。

### 4.3 通用约定

- 统一返回结构：`{ code, message, data }`
- 全局异常处理：业务异常返回友好提示，未捕获异常返回通用错误
- 状态枚举：桌台状态、订单状态、明细状态、角色的枚举值与 business-process.md 第 2 章状态机一一对应，为全项目唯一权威来源

## 5. 前端结构

### 5.1 页面清单

| 页面 | 路由 | 需求依据 |
|---|---|---|
| 登录页 | /login | AUTH-01 |
| 首页（模块入口大厅） | / | AUTH-03：固定展示全部业务模块 |
| 桌台看板 | /table | TABLE-01，轮询刷新 |
| 点餐页 | /table/order/:tableId | POS-01 ~ POS-04，从桌台进入 |
| 订单列表 | /orders | ORDER-05 |
| 结账页 | /checkout/:orderId | PAY-01 ~ PAY-04，从桌台看板进入 |
| 厨房 KDS | /kitchen | KDS-01 ~ KDS-03，轮询刷新 |
| 基础数据维护 | /base | BASE-01 ~ BASE-04 |
| 用户管理 | /users | AUTH-04 |

### 5.2 目录结构

```
src
├── api/          # 接口封装（按模块分文件）
├── stores/       # Pinia：登录状态、购物车
├── router/       # 路由（含登录状态检查）
├── layout/       # 主布局
└── views/        # 页面（按模块分目录）
```

### 5.3 权限的前后端分工

- **前端**：菜单固定展示；登录状态失效时跳转登录页——仅负责展示优化
- **后端**：所有接口的最终权限校验，**不能相信前端**——AUTH-03 的权威实现

## 6. 关键技术决策

| 需求依据 | 技术决策 |
|---|---|
| AUTH-01 登录状态保持 4 小时 | JWT，有效期 4 小时；前端存 localStorage；每次请求携带，后端校验 |
| AUTH-02 登出当前客户端失效 | 前端清除本地登录态，该客户端后续请求不再携带凭证（JWT 无状态） |
| AUTH-03 模块权限校验 | 后端接口声明所需模块权限，统一拦截校验；前端不做权限拦截 |
| AUTH-04 停用用户 | 停用仅影响登录；已签发的 token 在 4 小时有效期内仍可操作（JWT 无状态，V1 接受） |
| NF-04 数据 5 秒内自动更新 | 前端轮询（间隔 3~5 秒），桌台看板与 KDS 采用同一方案 |
| NF-01 金额精确 | Java BigDecimal；MySQL DECIMAL |
| NF-05 密码不明文 | BCrypt 哈希存储 |
| NF-02 状态一致性 | 开台、下单、结账、反结账、清台等关键操作使用数据库事务 |
| NF-03 操作留痕 | 业务表记录操作人、操作时间字段 |

## 7. 运行形态

- 开发环境：前端 Vite dev server、后端 Spring Boot dev、本地 MySQL
- 跨域：开发期由 Vite 代理转发到后端
- 不涉及生产部署（学习项目本地运行）

## 8. 架构约束

- **不做**：微服务、缓存、消息队列、分布式锁、多门店等超出 V1 范围的技术（对应 project-overview.md 3.2 与"简单优先"原则）
- **引入新技术的门槛**：须经用户确认，并同步更新本文档与 CHANGELOG.md
